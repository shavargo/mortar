# Cathedral Levels and Town — Design

Date: 2026-10-14
Status: Approved design, pending implementation plan

This is build-order step 2 of `docs/superpowers/specs/2026-10-14-arpg-framework-design.md`:
cathedral-style dungeon levels 1–4 and a town, generated by `Mortar.Core`, plus the minimal
`Mortar.Game` wiring that makes the town playable as depth 0.

## Decisions

- **Scope:** generation plus minimal game wiring. Vendors, Town Portal, doors that open and
  close, and Unity work are out of scope.
- **Cathedral levels:** content first. Keep the existing indoor room stitching and author a
  cathedral room set and one area file per depth. Add only the Core features the content needs.
- **Town:** one hand-drawn map, the same every game, loaded through a new `fixed` area mode.

The ground rules of the framework spec still apply: clean-room, MIT, no Blizzard or Diablo
names, deterministic, no file over 300 lines, no function over 50 lines.

## 1. `Mortar.Core` features

### 1.1 Multi-slot filler rooms

Filler and dead-end rooms may span 2×1, 1×2, or 2×2 slots (today only landmark rooms may).

- `RoomFiller` scans slots in row-major order as it does now. At each used, unplaced slot it
  considers every filler or dead-end room anchored with its top-left slot there.
- A multi-slot room fits only if every slot it covers is used and unplaced, and its doors cover
  every required opening on its outer edge, meeting any already-placed neighbours.
- Openings between two slots the room covers are inside the room and need no door.
- Dead-end preference stays as it is: a slot with exactly one opening tries dead-end rooms first.
  Multi-slot dead ends are allowed and follow the same rule using their outer openings.
- The existing layout validation (flood fill from the entrance reaches every marker) still
  rejects any bad result, which triggers a retry.
- The area compiler's requirement of at least one single-slot filler or corridor stays, so every
  slot can always be filled by a 1×1 room.

### 1.2 Room weights

- A room file may set `weight`, an integer from 1 to 1000. The default is 1.
- Landmark, filler, and dead-end picks become weighted picks with the existing generator.
- When every candidate in a pick has weight 1, the pick uses the existing uniform `Pick`, so
  existing sample layouts and their fingerprints are unchanged. A snapshot test pins this.

### 1.3 `fixed` area mode

- `mode: "fixed"` with `map`: a path to one room-format file (grid plus optional tags) that is
  used as the whole level.
- A fixed area has exactly these fields: `id`, `mode`, `tileset`, `map`. Supplying `graph`,
  `slotSize`, `rooms`, `maxSideBranches`, `targetSize`, or `maxAttempts` is an authoring error.
- The map's size is free (it is not tied to the slot-size formula), up to the existing layout
  dimension limit.
- `D` door characters are not allowed in a fixed map (there is nothing to connect).
- Generation stamps the map as drawn, resolves tile types from corners, picks variants from the
  seed, and records attempt 0. The fingerprint therefore differs per seed only through variants.
- All validation happens when the area is compiled, so a fixed area that compiles always
  generates. Compile errors: missing or invalid `map`; unknown character; no entrance or more
  than one entrance; a marker not on a walkable cell; a marker unreachable from the entrance.
  Unreachable walkable pockets are converted to `void`, as in indoor mode.

### 1.4 Custom markers

- A tileset may declare `markers`: a list of `{ "char": "H", "kind": "healer" }`.
- Custom markers behave like the built-in six (`E X B W S C`): the cell under them becomes the
  tileset's required `floor` ground, as marker cells do today, and they appear in the layout's
  marker list with their kind.
- Errors: a custom marker character that is a ground character, `D`, a built-in marker
  character, or a duplicate; an empty or duplicate kind; a kind equal to a built-in kind.
- Marker character lookup moves from the static `MarkerChars` table to a per-tileset lookup that
  starts from the built-in six and adds the custom ones.

### 1.5 Preview colours

`mortar preview` gives unknown ground types a stable colour derived from a hash of the ground id,
so new tilesets render without code changes. Known colours stay as they are.

## 2. Content

All new files live under `content/`. `samples/` stays unchanged as the level-generator demo.

### 2.1 Cathedral

- `content/tilesets/cathedral.json`: `void`, `floor`, `wall`, with variant weights.
- `content/rooms/cathedral/`: about 22 original rooms, slot size 9.
  - Landmarks: entrance chamber with up stairs (`E`), exit chamber with down stairs (`X`), a
    shrine (`W`, tag `waypoint`) used as the mid-level landmark, and a 2×2 boss chamber (`B`).
  - Single-slot fillers: north–south corridor, east–west corridor, crossroads, chapel, pillared
    room, collapsed room, cell block.
  - Multi-slot fillers: a 2×1 and a 1×2 pillared nave, and a 2×2 great hall, weighted lower than
    the single-slot fillers.
  - Dead ends: alcove, crypt niche, small shrine.
  - Rooms carry spawn markers (`S`) so monsters spread through the level, and an occasional
    chest marker (`C`) for later use.
- `content/areas/cathedral-1.json` … `cathedral-4.json`, all using the cathedral rooms:

| Depth | Target size (±15%) | Side branches | Graph |
|---|---|---|---|
| 1 | 49×49 | 3 | entrance → shrine → exit (paths), entrance → exit (branch) |
| 2 | 57×57 | 4 | as depth 1 |
| 3 | 65×65 | 6 | as depth 1 |
| 4 | 73×73 | 8 | entrance → shrine → boss → exit (paths), entrance → exit (branch) |

Sizes are `8n + 1` so the slot grid (stride 8) covers the whole target; with 48 the grid is one
slot short and every attempt would be too small.

- `content/levels.json` points depths 1–4 at these areas and keeps the current spawns and the
  depth-4 boss.

### 2.2 Town

- `content/tilesets/town.json`: the required `void`, `floor` (paving stones, used for the
  square and under markers), and `wall` (buildings), plus walkable `grass` and `road`, and
  `water` and `tree` (not walkable; walls and trees block sight). Custom markers `F` smith,
  `H` healer, `G` sage.
- `content/areas/town.json`: `mode: "fixed"`, `map: "../maps/town.json"`.
- `content/maps/town.json`: an original hand-drawn town of about 48×48 with a few buildings,
  a stream with a bridge, roads, the player start (`E`) in the town square, the dungeon entrance
  (`X`) at the cathedral steps on the east side, and the three vendor markers beside their
  buildings.

### 2.3 Reliability

A failed level blocks descent, so every cathedral area must generate on each of 500 consecutive
seeds (each with its normal retries). This is stricter than the 80% sample target in
`docs/design.md`. `maxAttempts` per area is raised if needed to meet it.

## 3. `Mortar.Game` wiring

- `levels.json` gains `"town": { "area": "areas/town.json" }`. The town entry accepts no
  `spawns` or `boss`. The loader requires the town's area to be `fixed` and its map to contain
  exactly one `E` and one `X`.
- `ContentSet` holds the town as the `LevelDefinition` for depth 0 (no spawns, no boss).
  `ContentSet.Level(0)` returns it; `DeepestLevel` stays the deepest dungeon depth.
- Depth 0 currently doubles as "no level entered yet" (`LevelEntry.Enter` checks
  `world.Depth != 0`). That is replaced by an explicit "has a current level" check.
- `World.Create` enters depth 0 at its entrance.
- Stairs: `X` in town leads to depth 1, arriving at `E`. `E` on depth 1 leads to town, arriving
  at `X`. `E` in town is rejected with "there is nothing above". The lowest depth becomes 0.
- The town spawns no monsters because its definition has none.
- Saves: depth 0 is valid on restore. The save version stays 1; the town is one more entry in
  the visited-levels list, and no saves exist outside development.
- `ScriptedPlayer` needs no special case: with no monsters in town it walks to `X` and descends.
  The determinism snapshot is regenerated because play now starts in town and the dungeon levels
  are new.

## 4. Errors

All authoring errors fail at load with file-qualified messages and no retries:

- room `weight` outside 1–1000;
- custom marker conflicts (section 1.4);
- fixed-area field and map errors (section 1.3);
- town entry with `spawns` or `boss`, a non-fixed town area, or a town map without exactly one
  `E` and one `X`.

Generation failures for cathedral areas retry as today and are reported with counted reasons.

## 5. Testing

- **Core:** multi-slot fillers (outer openings matched, covered slots filled, no overlap,
  dead-end rule); weighted picks (deterministic, bounds rejected); existing sample snapshots
  unchanged; fixed mode (stamped exactly, every compile error); custom markers (parsed, every
  conflict rejected); preview colour fallback.
- **Content:** each cathedral area succeeds on 500 seeds; one layout snapshot per cathedral
  area; the town compiles and its layout snapshot is pinned; shipped content loads cleanly.
- **Game:** new game starts in town at `E`; town ↔ depth 1 stairs both ways; `E` in town
  rejected; no monsters in town; a save made in town round-trips with an identical state hash;
  the regenerated determinism snapshot runs town → depth 1 → deeper.
- **CLI:** `generate` and `preview` succeed on the town and each cathedral area.
